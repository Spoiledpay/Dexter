# Sessão 2026-10-21 — D-19 fatia 2c (diagnóstico do `0xC0000005` no `win64 -native`)

Baseline no início da sessão: `git` limpo em `65ed71b` (1.2.407),
`build.bat` → 1.2.408, `tests\run_tests.bat` → **402/402 OK**.
Escopo desta fatia: **somente diagnóstico** (nenhuma mudança em `src/`).

## 1. Reprodução

```
out\dexter.exe tests\exc.exe -native -r -O tests\out\d19_2c.exe -o tests\out\d19_2c.asm -q
```

Avisos do pipeline (já na saída do nasm/link):

```
warning: uninitialised space declared in non-BSS section `.bss': zeroing [-w+zeroing]  (Nx)
d19_2c.obj : warning LNK4078: multiple '.bss' sections found with different attributes (C0300040)
d19_2c.obj : warning LNK4210: .CRT section exists; there may be unhandled static initializers
```

Resultado: `tests\exc.exe` → **42** (`caught=7 cleanups=6`);
`tests\out\d19_2c.exe` → **0xC0000005** (`-1073741819`).

## 2. Onde falta

`tests\dbg_probe.py tests\out\d19_2c.exe --ref tests\exc.exe`:

```
EXIT 0xC0000005 (-1073741819)
EXC  0xC0000005 ACCESS_VIOLATION em 0x0
RIP  rip=0x0
AV   execucao em 0x0
REGS rax=0x0 rcx=0x140010140 ...
STACK+00 q=0x1400028D8 rva=0x28D8 .text+0x18D8
```

O `rcx` é `.bss+0x140` (VA correta, via `lea rel`) e o `call` veio de
`.text+0x18D8`. Desmontando o original em `0x1400028BC`:

```
1400028BC  mov eax, [rip+0xc8a6]     ; guard em .bss+0x168
1400028C4  jne 0x1400028d9
1400028C6  lea rax, [rip+0xc873]     ; argumento (vira rcx)
1400028D0  mov rax, [rip+0xdb69]     ; IAT: orig 0x140010440 (.idata+0x440)
1400028D7  call rax                  ; rax = 0 no rebuild  -> AV
```

No `.asm` gerado (`tests\out\d19_2c.asm:3491`):

```
label_1400028D0:
    db 0x48, 0x8B, 0x05, 0x69, 0xDB, 0x00, 0x00  ; mov
label_1400028D7:
    call rax
```

`mov`-from-IAT cai em `db` (D-2: kinds 3/4 não existem). A `.idata` mudou de
`0x10000` para `0xE000`, mas o disp32 ficou congelado: `0x10440` agora é
`.bss` (zeros) → `call 0`.

## 3. Tamanho da classe (`tests/rip_audit.py`)

| alvo | `db`-blocks | sites falsos | seções alvo | mnemônicos |
|---|---|---|---|---|
| `hello` | 4 | **0** | — | — |
| `exc` | 810 | **42** | `.idata` 23, `.rdata` 19 | `mov` 23, `movsd` 18, `movq` 1 |
| `var64` | 822 | **47** | `.idata` 23, `.rdata` 19, `.rodata` 5 | idem |
| `notepad` | 12321 | **1252** | `.data` 1252 | `mov` 900, `lea` 132, `cmp` 96, `add` 22, `movzx` 13, `movdqu` 11, ... |

`var64` tem o mesmo AV (`EXC 0xC0000005` de execução em `0x0`,
`rcx=0x140010B20` = `.bss+0xB20`, return `.text+0x7698`). `hello` não tem
site falso — explica por que sempre passou.

Conclusão: a classe **não** é "mov-from-IAT"; é **qualquer** instrução que
cai em `db` e tem operando `[rip+disp32]`. Resolver só o `mov` não fecha a
D-19 (notepad continuaria com 1229 sites: `lea`, `cmp`, `movdqu`, ...).

## 4. Mecanismo viável (sonda)

`db 0x48, 0x8B, 0x05` + `dd target - $ - 4` no `nasm -f win64` gera
**relocação REL32**; o `link.exe` recalcula o disp. Verificado: a instrução
saiu `mov rax,[rip+0x2ff9]` → `.data+0x0` (seção movida pelo link) e o
executável linkou sem erro. Logo o fix é de emissão, não de pós-patch:
`db <bytes antes do disp>` + `dd label_<alvo> - $ - 4` +
`db <bytes depois do disp>`.

## 5. Suspeitos descartados

- **TLS**: a Directory do `exc` já é simbólica. Original: `Start/End`
  `0x140012000/08` (`.tls`), `Index` `.bss+0xD0`, `Callbacks` `.CRT+0x38`.
  Rebuild: `Start/End` `0x14000A968/70` (`.rdata+0x1968`, o link fundiu a
  `.tls`), `Index` `.bss+0xD0`, `Callbacks` `.CRT+0x38`. **Correto.**
- **`.CRT`**: `LNK4210` é aviso (MinGW usa `.CRT` como dado; não há
  init-array do MSVC). Será reavaliado depois do fix, com comportamento.
- **`.xdata`/`.tls` fundidos na `.rdata`**: esperado; os DataDirectories já
  são remapeados por (seção, offset) — `pe_dirs.py` 5/5.

## 6. Defeito independente confirmado

`.asm` emite `section .bss data` (progbits): `resb` vira zeros no arquivo
(`-w+zeroing`) e o link reclama `LNK4078`. No rebuild: `.bss` =
`CNT_INITDATA`, `rawsize=0xC00` (o original é `CNT_UNINIT`, `raw=0`).
No `var64` o `LNK4078` também atinge a `.idata` (reaberturas com classes
diferentes). Regra pretendida: `uninit`/`raw==0 && vsize>0` → `nobits`, e
classe decidida uma vez por nome de seção.

2. `.bss`/uninit `nobits` + classe por seção (mata `LNK4078` e o zeroing).
3. Gate novo `[57]`: `rip_audit` = 0 em `exc`/`var64`/`notepad`; `exc -native
   -r` → exit 42; `var64`/`notepad` linkam e rodam; `-m bin -native`

4. Só depois reavaliar `.CRT` (LNK4210) com comportamento observado.

Ferramentas desta fatia: `tests/secdump.py`, `tests/dbg_probe.py`,
`tests/rip_audit.py` (já usáveis isoladamente; entram no gate em A.2).

## 8. A.2 — implementação (mesma sessão)

Aprovado escopo completo + suíte lenta. Mudanças em
`src/disasm/emit_nasm.asm` e `src/gen/rebuild.asm`:

1. **kind 5 no emissor** (`dex_emit_insn`): `db <prefixo>` +
   `dd label_<alvo> - $ - 4 [- 0x<imm>]` + `db <imm>`. O `$` é o início do
   `dd`; o `- imm` existe porque o disp RIP é relativo ao **fim** da
   instrução. `-m bin` não usa kind 5 (layout preservado ⇒ disp congelado já
   correto; `fc /b` intacto).
2. **`.wcs_emit_db`** decide: x64, `disp_size==4`, `modrm&0xC7==5`,
   sem SIB/67, `g_rn != 0`, alvo na imagem e **com label garantido**
   (`.ptr_tgt_ok` p/ dados, `.code_tgt_ok` p/ código/bit D). Sem label → `db`.
   O 5º argumento (tva) vai em `[rsp+32]` (48 B reservados no caller) e é
   lido em `[rbp+48]` no callee.
3. **REX exato**: `call|jmp [mem]` com `has_rex` cai em `db` (o nasm
   descarta o REX.W/B e o encoding encolhe 7→6 B).
4. **`bss` nobits**: classe decidida por characteristics
   (`CNT_UNINIT` ou `raw==0 && vsize>0` → `bss`).

Bugs de implementação encontrados e corrigidos no caminho (nenhum ficou):
`[rbp+16]` em vez de `[rbp+48]` para o 5º arg; `cmp r13,0; je .as_db`
(impname nulo) desviava antes do kind 5.

Resultados: `rip_audit` exc **42→0**, var64 **47→0**, notepad 14
corrigíveis→0 (1238 limite); `label_drift` exc **0**; `.CRT` byte-idêntico;
`-w+zeroing`/`LNK4078 .bss` extintos; **`var64.exe -native -r` roda exit 0**
(era `0xC0000005`).

**Limite novo (medido):** `exc -native -r` continua AV, agora **dentro de
`libstdc++-6.dll+0x192190`** (execução em endereço não-executável), com
`.xdata` byte-idêntico e `.text` exato. Causa: as tabelas de exceção C++ do
GCC são **posicionais** (encodings pcrel no LSDA e nas seções `/NNN`, que o
link move) — não há relocação para offsets relativos entre seções.
Próximas fatias propostas:
- **2c-2**: `-native -r` em PE com personalidade C++ GCC → recusar com erro
  honesto (ou pós-patch pcrel). Enquanto isso, `-m bin -native` é o caminho
  fiel (exit 42).
- **2c-3**: `.data` com `vsize > raw_size` — emitir o tail zerado com labels
  (destrava as 1238 refs do `notepad`).
